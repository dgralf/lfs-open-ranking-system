# LFS Open Ranking System - Protocol Specification

This document provides the reference specification for the **LFS Open Ranking System** P2P and cryptographic protocol. It is intended for developers who wish to build custom bots, alternative web portals, or integrate their own services with the decentralized ranking network.

By adhering to this specification, any server client (written in Node.js, C#, PHP, etc.) can securely interact with the P2P Validator Nodes without relying on the reference Python implementation (`system.py`).

---

## 1. Cryptographic Authentication

The network enforces a zero-trust model for data ingestion. All critical state changes (like race results) must be mathematically signed by a **Trusted Server Identity**.

*   **Algorithm:** Ed25519 (Edwards-curve Digital Signature Algorithm).
*   **Key Format:** Raw bytes (32 bytes for private key, 32 bytes for public key), typically stored and transmitted as 64-character hexadecimal strings.
*   **Signature Target:** The exact raw bytes of the HTTP POST body (which is a JSON string).
*   **Transport:** The resulting 64-byte signature is encoded as a 128-character hex string and sent in the `X-Signature` HTTP header.

### Generating a Signature (Pseudo-code)
```python
payload_bytes = '{"action":"process_race_results", ...}'.encode('utf-8')
signature_bytes = ed25519_sign(private_key_bytes, payload_bytes)
headers = {
    "X-Signature": hex_encode(signature_bytes),
    "Content-Type": "application/json"
}
```

## 2. Validator Node Endpoints

The Validator Node exposes a REST-like API. The primary endpoint for state transitions is the Ingest API.

### `POST /api/api_ingest.php`
Accepts a JSON payload. Requires a valid `X-Signature` header matching a public key in the validator's `trusted_servers` list (except for actions that are designed for initial setup, like `redeem_server_token`).

#### Action: `process_race_results`
Submits the final results of a race to be processed for ELO calculation and stored in the decentralized ledger.

**Payload Structure:**
```json
{
  "action": "process_race_results",
  "track": "AS1",
  "server_name": "My LFS Server",
  "results": [
    {
      "uname": "player1",
      "position": 1,
      "total_time": 600123,
      "best_lap": 60123,
      "car": "XF GTR"
    },
    {
      "uname": "player2",
      "position": 2,
      "total_time": 610456,
      "best_lap": 61456,
      "car": "XR GT TURBO"
    }
  ]
}
```
> **Note:** Times are measured in integer milliseconds. A `total_time` of `0` denotes a DNF (Did Not Finish).

#### Action: `update_server_status`
Pushes live telemetry to the network (currently active players, session status).

**Payload Structure:**
```json
{
  "action": "update_server_status",
  "servers": [
    {
      "name": "My LFS Server",
      "ip": "1.2.3.4",
      "port": 63392,
      "track": "AS1",
      "status": "racing",
      "players": [
        {
          "uname": "player1",
          "car": "XFG",
          "position": 1,
          "lap": 5,
          "last_lap": "1:00.123",
          "split": "-"
        }
      ]
    }
  ]
}
```

#### Action: `generate_auth_code`
Requests a short-lived 8-character verification code used by players to link their in-game LFS username with their web portal account.

**Payload Structure:**
```json
{
  "action": "generate_auth_code",
  "uname": "player1"
}
```
**Response:** `{"status": "success", "code": "A1B2C3D4"}`

#### Action: `redeem_server_token`
Used during initial setup to exchange a web-generated Invite Token for network trust. **(Does not require X-Signature)**.

**Payload Structure:**
```json
{
  "action": "redeem_server_token",
  "token": "SRV-ABCD1234",
  "new_name": "My New Server",
  "new_key": "<64-character hex public key>"
}
```

## 3. P2P Network Protocol

Validator nodes form a gossip network to replicate state and race history.

### `POST /api/peer`
Registers a new node as a peer. The request must be signed by an already trusted server identity to prevent sybil attacks.
**Payload:** `{"address": "http://1.2.3.4:8080"}`

### `POST /api/vouch`
Allows an existing trusted server to cryptographically "vouch" for a new server identity, adding it to the trusted ledger globally via gossip.
**Payload:** `{"new_name": "Community Server", "new_key": "<hex public key>"}`

### `GET /api/races?since_id=<ID>`
Used by validators (and web portals) to sync the race ledger. Returns all cryptographic race records newer than `since_id`. 
The `signature` field in the response can be verified against the known `trusted_servers` to mathematically guarantee the race is legitimate.

---

## 4. Trust Model Summary

1.  The network starts with a Genesis Public Key (the primary server/admin).
2.  New servers can join by either:
    *   Redeeming an invite token generated by an admin on the Web Portal.
    *   Being "Vouched" for by an already trusted server via the P2P network.
3.  Once trusted, a server's public key is known by all nodes.
4.  Any race result submitted by that server is signed. If the server goes rogue, its public key can be revoked, instantly invalidating any future spoofed races.
