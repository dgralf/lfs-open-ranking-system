# Validation Process

The **LFS Open Ranking System** relies on a robust cryptographic validation mechanism to ensure no one can fake race results or manipulate driver ELO, even though it operates on a decentralized network.

## Cryptographic Flow of a Race

1. **Local Generation:** At the end of the race, the Bot Client of `Server A` generates a raw JSON file containing the positions, times (PBs), and track/mod information.
2. **Cryptographic Signature:** Before broadcasting, the Bot Client calculates the SHA-256 hash of these raw results and digitally signs it using its locally generated Ed25519 Private Key.
3. **Broadcast:** The Bot Client sends this package (Results + Hash + Signature) via a secure HTTP POST to the Validator Node (`/ingest`).
4. **Signature Verification:** The `Validator Node` receives the block. It queries its decentralized P2P SQLite ledger to obtain the public key linked to `Server A`. With it, it executes a mathematical algorithm to verify that the signature was indeed generated by the server owner and that the JSON hasn't been altered in transit.
5. **Consensus and Gossiping:** If the signature is correct and the times are logical, the `Validator Node` accepts the race. It adds its own timestamp, saves it to the immutable ledger (blockchain), and propagates it through the network to the other nodes so everyone has the same information.
6. **ELO Recalculation:** Immediately after successful verification, the scoring system kicks in, recalculating the ELO of all drivers involved based on their direct head-to-head matchups in the race.

## Centralized Onboarding, Decentralized Execution

To prevent malicious actors from spamming the network by creating fake servers, the system implements a hybrid authentication mechanism via **Invite Tokens**.

1. **User Authentication:** Server owners log into the official Web Portal using their verified LFS accounts.
2. **Token Generation:** They generate a unique `SRV-` Invite Token for their new server.
3. **Redemption & Key Generation:** The bot client boots up with this token. It securely generates its own Ed25519 cryptographic keys locally, and sends the Public Key to the Validator Node along with the Invite Token.
4. **Dual Sync:** The Validator verifies the Token, registers the server's Public Key into the immutable P2P ledger, and bridges the creation of the server back into the Web Portal's MySQL database. This ensures maximum security against botnets while keeping the onboarding process completely frictionless.

## Cheat Resistance

Since Validator Nodes do not blindly trust the incoming data:
- **Absurd Times:** If a server sends an impossible lap time for a given class, the validator can reject the block.
- **Identity Spoofing:** It is mathematically impossible for a server to "invent" a race on behalf of another, as it lacks its private Ed25519 Key.
- **Empty Races:** The ELO system requires a minimum number of real competitors; solo races are only used to record PBs (Personal Bests), but do not affect the competitive ranking.
